----------------------------------------------------
HOW THE RL ENVIRONMENT WORKS (RightArmRobot class)
----------------------------------------------------

The RightArmRobot class is the core of the project. It wraps the
PyBullet physics simulation into a standard Gymnasium RL environment.

Here is what happens at each stage:

1. __init__()
   - Sets up the action and observation spaces
   - Action space: 10 continuous values in [-1, 1], one per motor joint
   - Observation space: 19 continuous values in [-10, 10] (state vector)
   - Calls reset() to initialise

2. reset()
   Called at the start of every episode (and at init).
   - Picks a RANDOM target position (x in [-0.10, 0.15], y in [0.3, 0.65], z in [0.15, 0.35])
   - Picks a RANDOM target orientation (Euler angles -> rotation matrix -> quaternion)
   - Loads the robot URDF into PyBullet (or reuses the existing simulation)
   - Gets the robot's starting end-effector position and orientation from PyBullet
   - Calculates the initial distance and angle error to the target
   - Returns the 19-element observation vector

3. step(action)
   Called once per timestep. The RL agent sends an action; the environment
   applies it and returns the new state + reward.
   - Scales action: joint 0 (prismatic/linear) scaled by /4, joints 1-9 scaled by *pi
   - Applies dependent joint constraint: joint 2 = -joint 1 (physical coupling)
   - Sends joint position commands to PyBullet via setJointMotorControl2()
   - Steps the simulation 3 times (for stability)
   - Gets new end-effector position and orientation
   - Calculates reward (see reward section below)
   - Returns: observation, reward, terminated, truncated, info

OBSERVATION VECTOR (19 elements):
  [0]      Euclidean distance to target (metres)
  [1]      Quaternion dot product with target (orientation error proxy)
  [2-4]    Target position, normalised to [0,1]
  [5-7]    Current end-effector position, normalised to [0,1]
  [8-11]   Current end-effector orientation (quaternion, 4 values)
  [12-18]  Target orientation (quaternion, 4 values) — NOTE: Quat_t is (4,1) so .flatten() gives 4 values

ACTION SPACE (10 values):
  10 motorised joints out of the robot's total joints.
  Joint 0: prismatic (linear slide) — controls height/gantry
  Joints 1-9: revolute (rotation joints) — controls arm angles
  Joint 2 is dependent on joint 1 (mechanical constraint in real hardware)

REWARD FUNCTION (Phase 1 — position only):
  reward = -dn + 5.0 * (prev_dist - curr_dist)
  where dn = Euclidean distance normalised to [0,1] by dividing by 0.7533

  - "-dn": penalises being far from target (always negative)
  - "5.0 * (prev_dist - curr_dist)": progress reward — positive if getting closer,
    negative if moving away. This is the KEY improvement over the baseline.
  + 100.0 bonus if dist < 0.02m (success)

  Episode ends when:
  - TERMINATED: distance < 0.02m (success)
  - TRUNCATED: 300 steps reached without success

----------------------------------------------------
HOW SAC TRAINING WORKS
----------------------------------------------------

Soft Actor-Critic (SAC) is the RL algorithm used throughout this project.

Key concepts:
  - Off-policy: learns from a replay buffer of past experiences (not just the
    most recent episode). This makes it sample-efficient.
  - Entropy regularisation: encourages the agent to be "uncertain"/exploratory.
    The "soft" in SAC means it maximises reward + entropy, not just reward.
    This prevents it from getting stuck in local optima too early.
  - Continuous action space: unlike DQN (which picks discrete actions), SAC
    outputs real-valued joint angles directly.

Training loop (simplified):
  1. Agent observes state s
  2. Agent outputs action a (joint positions)
  3. Environment executes action, returns reward r and new state s'
  4. (s, a, r, s') stored in replay buffer
  5. Every step: sample a random batch from replay buffer, update neural networks
  6. Repeat for 500,000 timesteps

Neural network:
  - "MlpPolicy" = Multi-Layer Perceptron (fully connected neural net)
  - Input: 19-dimensional observation vector
  - Output: 10-dimensional action vector (joint positions)
  - SB3 uses default architecture: 2 hidden layers of 256 neurons each

----------------------------------------------------
CURRICULUM LEARNING (the key innovation)
----------------------------------------------------

The baseline (JRun / Warren's version) failed because:
  - Strict success criteria from the very start (must be within 0.02m)
  - The robot almost never randomly reached the target, so got no positive reward
  - No learning signal = no learning

The curriculum approach fixes this by starting easy and getting harder:

  Phase 1 (500k steps): Position only
    - No orientation requirement at all
    - Success = within 0.02m of target position
    - Terminal reward = +100
    - Result: ~30% success after 500k steps (vs 0.96% with baseline at start)

  Phase 2 (500k steps): Orientation fine-tuning
    - Loads Phase 1 weights and replay buffer
    - Adds orientation reward ONLY when already close to target (d < 0.03m gate)
    - This prevents orientation learning from disrupting position learning
    - RESULT: Failed — orientation did not converge
    - ROOT CAUSE: Several joints have asymmetric/restricted limits that make
      randomly-sampled orientation targets physically unreachable:
        Joint 6: only rotates between 1.571 and 3.578 rad (never goes below ~90 deg)
        Joint 8: only negative values, between -2.426 and -0.698 rad
      Fix needed: sample orientation targets only within the robot's reachable workspace

  Two-arm (2M+ steps across 4 phases): Cooperative dual-arm
    - Phase 1: curriculum target expansion (starts in small region, expands to full clinical)
    - Phase 2-3: tolerance ramping (0.05m -> 0.04m -> 0.02m)
    - Phase 4: both arms must reach same target simultaneously
    - Orientation was NEVER attempted for two-arm (too complex, left for future work)

HARDWARE INTEGRATION FRAMEWORK (already built, not tested)
----------------------------------------------------

The C++ code in Framework_for_Integration_into_Hardware/ describes how
the trained RL model will eventually drive the real robot.

The physical robot runs USRobotControl — a Qt6 C++ desktop application
that was built by Dr. Housden. It:
  - Communicates with Teensy microcontroller boards over USB serial
  - Accepts input from external devices (joystick, spacemouse, etc.)
  - Runs an inverse kinematics (IK) solver to convert desired end-effector
    poses into joint angles

The RL model outputs joint angles directly (NOT end-effector poses), so
the IK solver must be bypassed. The previous group built:

  RLInput.cpp:
    - TCP server listening on port 12345 (default)
    - Python RL model connects as a client
    - Receives JSON: {"joint_angles": [j0, j1, ..., j21]}
    - Emits a Qt signal when valid joint angles received

  RobotControl::setJointAnglesFromRL():
    - New slot that bypasses the IK solver entirely
    - Applies joint limit checking (isPoseInRange)
    - Applies collision checking (GJK algorithm — isCollision)
    - Maps 22 kinematics-order joints to 17 physical motor ports
    - Sends to motors via moveAllAbsolute()

  rl_test_client.py:
    - Python script that connects to the TCP server
    - Sends test joint angle sequences to verify the pipeline works
    - Used to validate the framework without needing the real RL model
