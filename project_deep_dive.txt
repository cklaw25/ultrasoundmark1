SECTION 1 — WHAT THIS PROJECT ACTUALLY IS
====================================================

The goal is to build a robot that can perform an ultrasound
scan on a pregnant patient's abdomen — automatically,
without a human sonographer holding the probe.

WHY IS THAT HARD?
An ultrasound probe must be:
  1. Pressed against the skin at the RIGHT POSITION (x, y, z)
  2. Held at the RIGHT ANGLE (orientation) — if you tilt the probe
     even slightly, the ultrasound image blurs or disappears
  3. Done WITHOUT the two arms colliding with each other

THE ROBOT HARDWARE:
There are TWO robotic arms mounted above the patient, both
working together. Each arm is physically described by a URDF
file (Unified Robot Description Format) — this is an XML file
that describes the robot's links (rigid segments) and joints
(where they connect).

DOF COUNT:
Each arm has 10 joints (joint indices 0–9):
  - Joint 0:  Prismatic (slides up and down like a rail — gantry height)
  - Joints 1–9: Rotational (spin around an axis)
  - SPECIAL RULE: Joint 2 is always = -Joint 1
    (they are mechanically coupled, one gear driving the other)
    So each arm has 9 INDEPENDENT degrees of freedom.

Two arms × 9 independent joints = 18 independent DOF.
(You said 16 or 17 — close. The URDF has 10 per arm = 20 total
joints, minus the 2 coupled ones = 18 truly independent.)

The simulation engine is PyBullet — a physics engine that
simulates gravity, joint physics, and collision detection.
Think of it as a virtual copy of the real robot that the
AI can practice on without breaking anything.


====================================================
SECTION 2 — WHAT IS REINFORCEMENT LEARNING (RL)?
====================================================

RL is a way of teaching a computer to make decisions by
giving it rewards and punishments instead of telling it
exactly what to do.

THE LOOP (the core idea):
  1. The agent (the AI) observes the STATE of the world
     (e.g., "I am 0.3m away from the target")
  2. The agent takes an ACTION
     (e.g., "move joint 3 by 0.2 radians")
  3. The environment responds — the state changes
  4. The agent receives a REWARD (positive = good, negative = bad)
  5. Repeat thousands of times

Over time the agent learns which actions in which states
tend to lead to higher cumulative reward. It does NOT get
told "do this" — it figures it out purely from trial and
error, guided by the reward signal.

WHY NOT JUST USE TRADITIONAL PROGRAMMING?
For a robot with 18 DOF, writing rules like "if you are 0.3m
away, move joint 5 by X" is impossibly complex. The space of
all possible arm configurations is enormous. RL learns to
navigate that space on its own.

ANALOGY: Training a dog.
  - You don't explain to the dog HOW to sit.
  - You just say "sit" (give a cue/state),
    and if the dog sits, you give it a treat (reward).
  - After enough repetitions, the dog learns.
RL is the same principle, but for math instead of dogs.

KEY TERMS:
  Agent       = the AI that makes decisions (the SAC model)
  Environment = the simulated robot + PyBullet world
  State       = what the agent observes right now
  Action      = what the agent decides to do
  Reward      = the score the agent gets for that action
  Episode     = one full attempt from start to timeout/success
  Policy      = the agent's strategy (a neural network that
                maps state → action)

SECTION 3 — WHY SAC WAS CHOSEN — AND WHAT SAC DOES
====================================================

SAC = Soft Actor-Critic

There are many RL algorithms. SAC was chosen because:
  a) It works well with CONTINUOUS actions (joint angles
     can be any real number in a range, not just "left/right")
  b) It is SAMPLE EFFICIENT — learns from fewer timesteps
     than older algorithms like PPO or DDPG
  c) It automatically explores (the "soft" / entropy part)
     so it doesn't get stuck always doing the same thing
  d) It is stable to train — doesn't suddenly forget
     everything it learned

HOW SAC WORKS — THREE PARTS:

PART A: THE ACTOR (Policy Network)
  A neural network that takes the state as input and
  outputs an action. In SAC, it doesn't output ONE action —
  it outputs a DISTRIBUTION (a range of possible actions
  with probabilities). This is what makes SAC "stochastic"
  (random exploration built in).

  In code: model.predict(obs) uses the actor network to
  sample an action from that distribution.

PART B: THE CRITIC (Value Network)
  Another neural network that answers the question:
  "How good is it to take action A in state S?"
  SAC actually uses TWO critics and takes the minimum of
  their predictions — this prevents overconfidence/instability.

  The critic estimates Q(s, a) = "expected future reward
  if I take action a in state s, then act optimally forever."

PART C: ENTROPY REGULARISATION (the "Soft" part)
  SAC adds a special term to the reward:
    reward_effective = reward + alpha * entropy

  Entropy = how random/spread-out the action distribution is.

  A HIGH entropy means the agent is exploring widely.
  A LOW entropy means the agent is very confident.

  Alpha (ent_coef in the code) controls this balance.
  SAC automatically tunes alpha during training (that's why
  you see "ent_coef: 0.915" in the logs — it's adjusting).

  WHY DOES THIS HELP?
  Without entropy regularisation, the agent tends to
  converge on ONE solution and never explore alternatives.
  For a robot arm, there are MANY ways to reach a target —
  entropy helps SAC find a robust strategy, not just one.

THE TRAINING LOOP IN DETAIL:
  1. Agent takes an action → environment steps forward
  2. (state, action, reward, next_state) stored in REPLAY BUFFER
  3. Every step, sample a random BATCH from the replay buffer
  4. Update the CRITIC networks using the batch
  5. Update the ACTOR network to take actions the critic rates highly
  6. Update alpha (entropy coefficient) to hit target entropy
  7. Repeat

The replay buffer is why SAC is "off-policy" — it can learn
from old experiences, not just the current episode. This
makes it much more efficient than on-policy methods.

SECTION 4 — SAC IN REAL LIFE (Not Just This Robot)
====================================================

SAC is one of the most popular continuous RL algorithms.
Real-world and research examples:

1. DEXTROUS HAND MANIPULATION (OpenAI Rubik's Cube)
   Teaching a robotic hand to solve a Rubik's cube by
   manipulating it with fingers — exactly the kind of
   high-DOF continuous control this project needs.

2. LEGGED LOCOMOTION (Boston Dynamics style)
   Training robot dogs to walk on rough terrain.
   SAC handles the continuous leg joint angles naturally.

3. AUTONOMOUS DRIVING
   Controlling steering angle and throttle (continuous)
   to navigate roads without crashing.

4. HVAC OPTIMISATION (Google DeepMind)
   SAC was used to control cooling systems in data centres,
   reducing energy use by ~40%. The "actions" were fan speeds
   and valve positions — all continuous.

5. MOLECULAR DRUG DESIGN
   SAC used to explore chemical space and design molecules
   that bind to target proteins. The "actions" are atomic
   modifications to a molecule.

6. TRADING / PORTFOLIO MANAGEMENT
   Continuous action = how much of each asset to hold.

COMMON THREAD: anywhere you have continuous decisions,
a reward you can define, and a simulator or real-world
feedback loop — SAC is a natural choice.


====================================================
SECTION 5 — WHAT ARE TIMESTEPS?
====================================================

A TIMESTEP is a single forward step of the simulation.

In this robot's code:
  1. The agent picks a 10-element action (joint angles)
  2. PyBullet applies those joint targets to the robot
  3. PyBullet runs the physics for 3 simulation ticks
     (the "for _ in range(3): stepSimulation()" loop)
  4. The new position and orientation of the end effector
     are read back
  5. A reward is computed
  6. That whole thing = 1 TIMESTEP

An EPISODE is a sequence of timesteps that ends either:
  - TERMINATED: the robot reached the target (success!)
  - TRUNCATED: max_step_size reached (300 steps = timeout)

So one episode = up to 300 timesteps.

When we train for 500,000 timesteps:
  - That's roughly 500,000 / 300 ≈ 1,667 episodes
  - But successful episodes end before 300 steps,
    so there could be more episodes if success happens early

The training progress bar in your output shows
"Step 28900/150000" — that means 28,900 individual
forward-simulation-reward-compute cycles have happened.


====================================================
SECTION 6 — WHAT IS AN END EFFECTOR?
====================================================

In robotics, an END EFFECTOR is the last piece of the robot
— the part that actually does the work.

For a human arm:
  Base = shoulder, Joints = elbow/wrist, End effector = HAND

For this ultrasound robot:
  Base = the fixed mounting rail, Joints = the 10 arm joints,
  End effector = the ULTRASOUND PROBE at the tip

In code, this is link_index = num_joints - 1 (the last link).
That's what getLinkState() reads — the position and
orientation of the probe tip.

All the rewards and success conditions are about where
this probe tip is, not about the individual joint angles.
The RL agent has to figure out which joint angles produce
the desired probe tip position — that's the hard part.


====================================================
SECTION 7 — VOCABULARY AND TERMINOLOGY GLOSSARY
====================================================

QUATERNION
  A way of representing 3D rotation using 4 numbers (w, x, y, z).
  Better than Euler angles for robotics because it avoids
  "gimbal lock" (a situation where two rotation axes align
  and you lose a degree of freedom).
  Think of it as coordinates on a 4D sphere — every possible
  rotation maps to a unique point on that sphere.
  In code: orientation = np.array(link_state[1]) → 4 values

EULER ANGLES
  Another way to represent 3D rotation using 3 angles (roll,
  pitch, yaw) — like how a plane's orientation is described.
  Intuitive, but mathematically tricky for robotics.
  This project uses Euler angles to GENERATE target orientations,
  then converts them to quaternions for computation.

EUCLIDEAN DISTANCE
  The straight-line distance between two 3D points.
  distance = sqrt((x2-x1)^2 + (y2-y1)^2 + (z2-z1)^2)
  In the code: math.dist(self.position, self.pos_target)
  This is how far the probe tip is from the target position.

QUATERNION DIFFERENCE
  The angular gap between two orientations.
  If the probe is pointing right and the target wants it
  pointing up, the quaternion difference is the angle
  you'd need to rotate to close that gap.
  Measured in radians. 0 = perfect match. π (~3.14) = 180°.

FK (FORWARD KINEMATICS)
  Given the joint angles → compute where the end effector IS.
  This is what PyBullet's getLinkState() does.
  Easy direction: angles → position.

IK (INVERSE KINEMATICS)
  Given a desired position → compute what joint angles to use.
  Hard direction: position → angles (often multiple solutions
  or no solution).

CLINICAL WORKSPACE
  The physical region in 3D space where the ultrasound probe
  must operate. Bounded by:
    x: [-0.10, 0.15] metres
    y: [0.30,  0.65] metres
    z: [0.15,  0.35] metres
  This represents the area above a patient's abdomen.

URDF (Unified Robot Description Format)
  An XML file that defines the robot: links (rigid bodies),
  joints (connections), and their physical properties.
  File used: RightArm.urdf (single arm) / TwoArms_col.urdf (dual arm)
  col = collision geometry included

NORMALISATION
  Scaling a number so it falls between -1 and +1.
  Neural networks train better with normalised inputs.
  Formula: x_n = (2 * (x - min) / (max - min)) - 1
  Example: x = 0.0 in range [-0.10, 0.15]:
    x_n = (2 * (0.0 - (-0.10)) / (0.15 - (-0.10))) - 1
         = (2 * 0.10 / 0.25) - 1
         = 0.8 - 1 = -0.2

REPLAY BUFFER
  A memory bank that stores past (state, action, reward,
  next_state) tuples. SAC samples random batches from this
  during training to learn from past experience.
  This is what gets saved as replaybuffer.zip

ENTROPY (in SAC context)
  A measure of randomness in the policy's actions.
  High entropy = the agent tries many different actions.
  Low entropy = the agent is very decisive/repetitive.
  SAC encourages high entropy early (exploration) and
  automatically reduces it as the policy improves.

POLICY
  The agent's decision-making strategy — technically a
  neural network that maps state → action probabilities.
  "The policy" and "the model" are often used interchangeably.

EPISODE
  One complete attempt: start → (success or timeout).

TERMINATION
  Episode ended because the robot SUCCEEDED (reached target).

TRUNCATION
  Episode ended because the robot RAN OUT OF TIME (max steps).

CONVERGENCE
  When training metrics stabilise and stop improving.
  A converged model has "learned as much as it can" with
  the current setup.

POSITION TOLERANCE (pos_tol)
  Success threshold for position: 0.02m (2cm).
  If end effector is within 2cm of target = position success.

ORIENTATION TOLERANCE (orient_tol or ORIENT_TOL)
  Success threshold for angle: in Phase 2 = 1.2 radians (~68°).
  Relaxed compared to the original 0.2 rad because orientation
  is hard and we want the agent to see SOME successes early.


====================================================
SECTION 8 — HOW THE ROBOT IS DESCRIBED IN CODE (STATE)
====================================================

The OBSERVATION (= state) is a 19-element vector.
This is what the neural network SEES each timestep.

Here is each element explained:

Index  Value                           Why it's included
-----  -----                           -----------------
0      Euclidean distance (m)          How far is the probe from target?
1-4    Quaternion difference (4 values) How misaligned is the orientation?
5-7    Target position (normalised)    Where does the probe need to go?
8-10   Current position (normalised)   Where is the probe right now?
11-14  Current orientation quaternion  Which way is the probe facing?
15-18  Target orientation quaternion   Which way should it face?

WHY 19 ELEMENTS?
1 (dist) + 4 (quat_diff) + 3 (target pos) + 3 (current pos)
+ 4 (current orn) + 4 (target orn) = 19

KEY DESIGN DECISION: The observation includes BOTH absolute
positions (target and current) AND relative distance.
The agent can use the relative distance for rewards, and
the absolute positions to learn the geometry of the workspace.

In code (run_phase2.py and the notebooks):
  obs = np.concatenate([
      [self.Euclid_dist],           # index 0
      Quat_diff_Q.flatten(),        # indices 1-4
      pos_target_n,                 # indices 5-7
      pos_n,                        # indices 8-10
      self.orientation,             # indices 11-14
      self.Quat_t.flatten()         # indices 15-18
  ])

For the TWO-ARM robot (TwoArm.ipynb), the observation is
45 elements — roughly doubling up for both arms plus joint states.


====================================================
SECTION 9 — HOW THE ROBOT ACTS (ACTION SPACE)
====================================================

The ACTION is a 10-element vector, one number per joint.
Each number is in range [-1, +1] (the neural network outputs
values in this normalised range).

HOW THE ACTION IS SCALED (in the step() function):

  scaled_action[0] = action[0] / 4.0
    → Joint 0 is the prismatic (linear) gantry. Small scale
       because a small prismatic movement = big effect.

  scaled_action[i] = action[i] * pi  (for joints 1-9)
    → Rotational joints. Output range becomes [-π, +π] radians.
       That covers a full rotation in either direction.

  scaled_action[2] = -scaled_action[1]
    → Joint 2 is mechanically coupled to joint 1.
       They always move together in opposite directions.
       The RL agent outputs joint 2's action but it gets
       overridden — effectively joint 2 is not independent.

In code (run_phase2.py):
  scaled = action.copy()
  scaled[0] = action[0] / 4
  for i in range(1, 10):
      scaled[i] = action[i] * np.pi
  scaled[2] = -scaled[1]

These scaled angles become the TARGET POSITION for each joint
motor — PyBullet's position controller moves each joint
TOWARD that target during the 3 simulation steps.


====================================================
SECTION 10 — HOW THE ROBOT IS SCORED (REWARD FUNCTIONS)
====================================================

This is the most important section. The reward is the SIGNAL
that teaches the robot everything. Bad reward = bad learning.

--- UTILITY FUNCTIONS FIRST ---

1. EulerToRMat(Euler)
   WHAT: Converts Euler angles [rx, ry, rz] to a 3x3
         rotation matrix.
   WHY: Rotation matrices are used as an intermediate step
        before converting to quaternions. The math is standard
        trigonometry — each entry is a product of sines and
        cosines of the three angles.

   The matrix looks like:
     R[0,0] = cy*cz   (cy = cos(roll), cz = cos(yaw), etc.)
   It represents "how does each axis get rotated?"

2. RMatToQuat(RMat)
   WHAT: Converts a 3x3 rotation matrix to quaternion [w,x,y,z].
   WHY: Quaternions are easier to compute differences with.
   HOW: The 4 quaternion components are derived from the
        diagonal entries of R. The abs() is to prevent sqrt
        of a tiny negative number from floating-point errors.

   q[0] = 0.5 * sqrt(1 + R[0,0] + R[1,1] + R[2,2])  (= w)
   Signs for x, y, z come from off-diagonal R entries.

3. quatDiff(q1, q2)
   WHAT: Computes the angular difference between two orientations.
   HOW:
     a) Compute qd = q2 * conjugate(q1)
        (quaternion multiplication to "subtract" orientations)
     b) The w-component of qd (= qd[0]) = cos(angle/2)
     c) angle = 2 * arccos(qd[0])

   RESULT: A single angle in radians representing how far
   apart the two orientations are. This is what you see in
   the training log as "Angle 2.825rad".

   The code clips qd[0] to [-1, 1] before arccos to avoid
   NaN from floating-point numbers slightly outside [-1, 1].

4. normalise(x, min_val, max_val)
   Formula: (2 * (x - min) / (max - min)) - 1
   Maps any value in [min, max] to [-1, +1].
   Used to put positions on the same scale as other observations.

--- PHASE 1 REWARD (position-only) ---

In progressnew_1-.ipynb and run_one_arm.py:

  Euclid_dist_n = clip(Euclid_dist / 0.7533, 0, 1)
    → Normalise distance. 0.7533m is the diagonal of the
      clinical workspace (maximum possible distance).
      So Euclid_dist_n = 1.0 means "as far as possible",
      Euclid_dist_n = 0.0 means "at the target".

  reward = -Euclid_dist_n                 (penalty for being far)
         + 5.0 * (prev_dist - curr_dist)  (bonus for getting closer)

  TERM 1: -Euclid_dist_n
    Constant penalty for being away from target. This pushes
    the agent to minimise distance at ALL times.
    Range: 0 (at target) to -1 (maximum distance away).

  TERM 2: 5.0 * progress
    Bonus for moving CLOSER to the target this step.
    If the arm moved 0.01m closer → reward += 5.0 * 0.01 = 0.05
    If the arm moved 0.01m farther → reward += 5.0 * (-0.01) = -0.05
    Multiplier 5.0 makes progress-chasing more attractive than
    just sitting still (which gives reward = -dist, a constant).

  ON TERMINATION (success):
    reward += 100.0
    Big positive bonus for reaching target. This is the "jackpot"
    that motivates the whole training.

--- PHASE 2 REWARD (position + orientation) ---

In progressnew_2_.ipynb and run_phase2.py:

  Same position terms as Phase 1, PLUS:

  POS_GATE = 0.03  (3cm)

  in_gate = (Euclid_dist < POS_GATE)

  if in_gate:
    orient_n = clip(Quat_diff_angle / (2*pi), 0, 1)
    reward += -ORIENT_W * orient_n                    (= -0.05 * angle)
    reward += ORIENT_PROG_W * (prev_angle - curr_angle) (= 0.5 * progress)

  WHAT THE GATE MEANS:
  Orientation rewards only turn on when the robot is already
  within 3cm of the target position. This is intentional —
  if you try to optimise both at once from the start, the
  agent gets confused and does neither well.
  It must FIRST learn to get close, THEN learn to rotate.

  ORIENT_W = 0.05: Small constant penalty for bad orientation.
  Much smaller than position penalty (~0.05 vs up to 1.0) so
  the agent still prioritises position.

  ORIENT_PROG_W = 0.5: Encourages the agent to actively reduce
  the angle error when inside the gate.

  DRIFT PENALTY:
  if (prev_dist < POS_GATE) and (curr_dist >= POS_GATE):
    reward -= 10.0  (DRIFT_PENALTY)

  This catches the case where the arm was inside the gate,
  started tuning orientation, but then accidentally drifted
  back out. The -10 penalty says: "don't lose your position
  while you're fixing orientation."

  ON TERMINATION (Phase 2 success):
    condition: Euclid_dist < 0.02 AND Quat_diff_angle < 1.2 rad
    reward += 100.0

  The 1.2 rad tolerance (~68°) is relaxed compared to the
  original 0.2 rad (≈11°) because the full orientation problem
  is very hard — we need the agent to see successes early.

--- TWO-ARM REWARD (TwoArm.ipynb) ---

  dist_L = distance of LEFT arm end effector from target
  dist_R = distance of RIGHT arm end effector from target

  current_max = max(dist_L, dist_R)  ← BOTTLENECK metric
  sum_dist    = dist_L + dist_R

  reward = (prev_max - current_max) * 100.0    ← bottleneck progress
         + (prev_sum - sum_dist) * 15.0        ← sum progress
         - 0.02                                ← time penalty (hurry up)
         - 0.045 * sum_dist                    ← absolute distance penalty
         - collisions * 0.5                    ← collision penalty

  WHY BOTTLENECK? The success condition requires BOTH arms
  to reach target. If you only reward the average distance,
  the model might park one arm at target and ignore the other.
  Max distance forces the model to fix the LAGGING arm.

  PROXIMITY BONUS (soft gate):
  soft = 1.35 * pos_tol
  if max(dist_L, dist_R) < soft:
    reward += 0.25 * (1 - prox/soft)
  Extra reward for being nearly there.

  ON TERMINATION:
    dist_L < pos_tol AND dist_R < pos_tol → reward += 260.0

SECTION 11 — CURRICULUM LEARNING
====================================================

Curriculum learning = training in stages, from easy to hard.
Like school: you learn addition before calculus.

In this project there are TWO kinds of curriculum:

A) STAGED TRAINING (Phase 1 → Phase 2)
   Phase 1: Train ONLY position (ignore orientation).
   Phase 2: Load Phase 1 model, add orientation rewards.

   WHY NOT TRAIN BOTH AT ONCE?
   If you show a student calculus on day 1, they learn nothing.
   The robot has the same problem — orientation tuning requires
   the robot to already be close to the position target.
   If it can't reach the target AT ALL, orientation reward
   is completely irrelevant and just confuses training.

B) WORKSPACE CURRICULUM (TwoArm.ipynb)
   The two-arm training uses a curriculum where the TARGET
   REGION grows larger over time:

     d = timesteps_elapsed / total_timesteps  (0.0 → 1.0)
     x_lo = interp(d, [0,-0.05])   y_hi = interp(d, [0.51, 0.62])
     etc.

   Early in training (d=0): small, easy-to-reach region.
   Late in training (d=1): full clinical workspace.

   This helps because the model first learns to reach "nearby"
   targets (short distances = simpler), then gradually has to
   reach "anywhere" in the workspace (longer, harder).

   The w_mid parameter also biases targets toward the
   geometric midpoint between the two arms' default poses,
   making dual-EE targets more reachable early in training.

CLINICAL CURRICULUM (mentioned in notebooks):
   There's a file called Clinical_R1_Maternal_Curriculum_Final
   — this was a more advanced curriculum the original team
   tried, likely incorporating realistic patient scan positions
   and a progressive sequence of difficulty levels.


====================================================
SECTION 12 — WHAT IS JRUN AND THE JRUN BASELINE?
====================================================

JRun is the name the original research team gave to their
main training notebook — it stands for "Joint Run" (or
possibly named after a person/experiment iteration).

From the directory listing visible in the notebooks:
  JRun.ipynb              ← main training notebook
  JRunbaseline20k.ipynb   ← 20,000-step baseline run
  JRunbaseline100k.ipynb  ← 100,000-step baseline run
  JRun_deterministic_evaluation.ipynb ← evaluation notebook

THE JRUN BASELINE is a COMPARISON POINT.

In research, when you propose an improvement (like curriculum
learning), you need to show it's BETTER than something simpler.
The baseline is the simplest possible version of training:
  - No curriculum
  - No orientation reward
  - No FK target sampling
  - Just: train SAC from scratch for X steps

The 20k and 100k versions are trained for different lengths
to see how the baseline evolves over time.

Then the improved version (with curriculum, FK sampling, etc.)
is compared against these baselines to show:
  "Our method achieves better final distance / more successes
   than the baseline at equivalent timesteps."

THE JRUN BASELINE EQUATION (what you see in results):
  It's just the Phase 1 reward with no Phase 2 or curriculum:

  reward = -Euclid_dist_n + 5.0 * progress_pos

  No orientation term, no gating, no collision penalty.
  This is what the robot can achieve with zero curriculum tricks.
  All improvements are measured against this.


====================================================
SECTION 13 — WHAT IS A TOLERANCE RAMP?
====================================================

A tolerance ramp is a technique where the success threshold
starts EASY and gets HARDER over time during training.

FROM TwoArm.ipynb (PosTolRampTwoArm class):

  POS_TOL_START_TRAIN = 0.18m  (18cm, very generous)
  POS_TOL_FINAL       = 0.13m  (13cm, tighter)
  POS_TOL_HOLD_TIMESTEPS = 500,000  (keep easy for first 500k steps)
  POS_TOL_RAMP_TIMESTEPS = 1,000,000  (ramp down over next 1M steps)

  PHASE 1 (0 → 500k steps): tolerance = 0.18m
    Easy. If BOTH arms within 18cm → SUCCESS.
    Agent sees lots of successes early → learns fast.

  PHASE 2 (500k → 1.5M steps): tolerance shrinks from 0.18 → 0.13m
    alpha = (elapsed - 500k) / 1M
    tol = 0.18 + alpha * (0.13 - 0.18) = 0.18 - alpha * 0.05

  PHASE 3 (1.5M+ steps): tolerance = 0.13m (held constant)

WHY NOT JUST TRAIN WITH 0.13m FROM THE START?
If you demand 13cm accuracy from episode 1, the robot
gets almost no success signal for hundreds of thousands of
steps. It can't learn from rare random successes.
By starting at 18cm, successes happen more often → faster
learning → then the goal gets harder as the model improves.

This is like teaching someone to shoot basketball:
First try from 1m away (almost impossible to miss),
then from 3m, then 5m, then game distance.

SECTION 14 — COLLISION PENALTY EXPLAINED
====================================================

From the collision_avoidance notebook:

WHAT COUNTS AS A COLLISION?
The robot body is split into two halves:
  Left arm links:  indices 2–10
  Right arm links: indices 12–20
  Base/gantry:     indices 0, 1, 11

Three types of collision are checked:

1. CROSS-ARM PROXIMITY (check_cross_arm_collision_env)
   For each pair (link from left arm, link from right arm),
   check if they are within threshold=0.02m (2cm) of each other.
   Each such pair adds 1 to proximity_penalty.

2. CROSS-ARM CONTACT (check_cross_arm_contact_env)
   For same pairs, check if they are ACTUALLY TOUCHING.
   Each contact pair adds 10 to contact_penalty.
   (Much heavier than proximity — touching is worse than near-miss)

3. ARM-BASE COLLISION (check_arm_base_collision_env)
   Check if either arm is within 2cm of the base/gantry.
   Adds 1 per pair to proximity_penalty.

TOTAL PENALTY:
  total_penalty = proximity_penalty + contact_penalty

In the reward function (collision_avoidance notebook):
  reward -= total_penalty * 5         ← proximity costs
  if contact_penalty > 0:
    reward -= 50                      ← hard contact costs extra

In TwoArm.ipynb (simpler version):
  collisions = len(bc.getContactPoints(bodyA=self.robot_id))
  reward -= collisions * 0.5

HOW DOES THIS DISCOURAGE COLLISION?
The agent is trying to MAXIMISE total reward.
Every time arms get within 2cm of each other:
  - reward -= 5 per pair (proximity)
Every time they touch:
  - reward -= 5 (proximity) + 50 (contact) = -55 per pair

Over an episode, repeated collision incurs cumulative penalty.
The agent learns: "getting the arms close to each other
costs me a lot of reward, so I should avoid it."

Over thousands of episodes, the policy naturally learns
trajectories that keep the arms separated.

SECTION 16 — WHAT "UNREACHABLE TARGET" MEANS
====================================================

This is the root cause of the ORIGINAL orientation problem
that motivated your Phase 2 fix.

THE ORIGINAL BUG:
The original notebooks sampled orientation targets using
random Euler angles:
  x_euler_t = random() * (-0.785398 - -2.35619)  → range roughly [-2.4, -0.8]
  y_euler_t = random() * (0.785398 - -0.785398)  → range [-0.8, +0.8]
  z_euler_t = random() * (pi - -pi)               → range [-π, +π]

Then converted to quaternion and used as target.

THE PROBLEM:
The robot's joints have limits in the URDF — each joint can
only rotate a certain amount (like your elbow can't bend
backwards). These are HARDWARE limits from the real robot
being modelled.

Joint 6 limit: [+1.5708, +3.5779] radians  (positive only!)
Joint 8 limit: [-2.4260, -0.6981] radians  (negative only!)

These asymmetric limits mean certain orientations in 3D space
are simply IMPOSSIBLE for the arm to achieve. But the original
code was generating targets randomly without checking this —
so it could ask the robot to face a direction that physically
no configuration of joints could produce.

ANALOGY: Imagine asking someone "touch your left shoulder with
your right hand by reaching backwards". Impossible. But the
code was constantly setting impossible goals like this.

WHAT YOUR FIX DID (FK-based target sampling):
Instead of:
  "Pick a random orientation, hope the robot can reach it"

Your fix does:
  1. Pick random joint angles WITHIN their URDF limits
  2. Use PyBullet FK (getLinkState) to find where the end effector
     actually ENDS UP with those angles
  3. Use that as the target position AND orientation

Now the target is GUARANTEED to be reachable — because it was
derived from a valid joint configuration.

The "FK sampling efficiency: avg 32 attempts per target" means
PyBullet has to try ~32 random joint configs before finding one
where the end effector lands inside the clinical workspace
(the 30cm x 35cm x 20cm target region). Each attempt takes
microseconds — this is still much faster than impossible targets.

SECTION 19 — DO I DO TESTING? WHAT DOES TESTING MEAN?
====================================================

YES, testing is separate from training and very important.

DURING TRAINING:
  The model is stochastic (random) — it explores.
  Rewards can be noisy.

TESTING (evaluation):
  model.predict(obs, deterministic=True)
  The "deterministic=True" makes the model use the mean of
  its action distribution — no randomness. This is what the
  real robot would do in deployment.

WHAT TO MEASURE IN TESTING:
  1. Success rate: N_success / 100 episodes (as %)
  2. Mean final Euclidean distance (m)
  3. Mean final orientation error (rad)
  4. Mean episode length (steps to reach target)
  5. Collision rate (steps with collision / total steps)

GOOD TESTING PRACTICE:
  - Test on UNSEEN targets (targets not used during training)
  - Run at least 100 episodes per test (statistics need large N)
  - Test deterministically, not stochastically
  - Compare to baseline (JRun results)

SECTION 20 — SAC TWEAKS: HOW TO CONTROL AND IMPROVE IT
====================================================

The SAC model is instantiated as:
  model = SAC("MlpPolicy", env, verbose=0)

Here are the parameters you can change and what they do:

1. LEARNING RATE (default 3e-4 = 0.0003)
   model = SAC(..., learning_rate=0.0001)

   Higher = learns faster but may overshoot / become unstable.
   Lower = more stable but slower convergence.
   Try: 0.0001 for finer tuning after Phase 2.

2. BATCH SIZE (default 256)
   model = SAC(..., batch_size=512)

   Larger batch = smoother gradient updates, needs more RAM.
   Try 512 if training is noisy.

3. ENTROPY COEFFICIENT (default "auto")
   model = SAC(..., ent_coef="auto")  ← automatic (recommended)
   model = SAC(..., ent_coef=0.1)     ← fixed exploration level

   If the model isn't exploring (always same action), increase.
   If the model is too random (not converging), decrease or let auto handle.

4. NETWORK ARCHITECTURE (default 2 layers of 64)
   Actually, stable-baselines3 SAC default is net_arch=[256, 256].
   The two-arm notebook uses:
     policy_kwargs = dict(activation_fn=torch.nn.ReLU, net_arch=[256, 256, 256])

   Deeper network (3 layers) = can learn more complex policies
   but needs more data and slower to train.

   For the single-arm problem, 2 layers of 256 is likely fine.
   For dual-arm, try 3 layers.

5. REPLAY BUFFER SIZE (default 1,000,000)
   model = SAC(..., buffer_size=500000)

   Larger buffer = remembers more past experiences.
   Usually leave at default.

6. GRADIENT STEPS (default 1 per step)
   model = SAC(..., gradient_steps=2)

   Number of gradient updates per environment step.
   Increasing to 2 can improve sample efficiency but is slower.

RECOMMENDED TWEAK ORDER FOR YOUR PROJECT:
  First: check if Phase 2 results are good before tweaking.
  Then: increase ORIENT_PROG_W in the reward before touching SAC.
  Then: try learning_rate = 0.0001 for fine-tuning.
  Then: try net_arch=[256, 256, 256] for the full dual-arm.
  Last resort: try a different algorithm (section 21).

SECTION 21 — OTHER RL ALGORITHMS TO CONSIDER
====================================================

1. TD3 (Twin Delayed Deep Deterministic Policy Gradient)
   LIKE SAC BUT: deterministic policy (no entropy bonus).
   PROS: Often slightly more stable than SAC.
   CONS: Requires careful noise tuning for exploration.
   TRY IF: SAC is training unstably or not exploring enough.
   In SB3: from stable_baselines3 import TD3

2. PPO (Proximal Policy Optimisation)
   The algorithm OpenAI used for robotics research.
   PROS: Very stable, good with sparse rewards.
   CONS: On-policy (can't use replay buffer), needs more timesteps.
   TRY IF: SAC keeps diverging/forgetting.
   In SB3: from stable_baselines3 import PPO

3. HER (Hindsight Experience Replay)
   NOT a standalone algorithm — an addon to SAC or TD3.
   PROS: EXTREMELY useful for robotic goal-reaching tasks.
   HOW IT WORKS: When the robot FAILS to reach the goal,
   HER "pretends" the position it ended up at WAS the goal
   and records that as a success. The robot learns:
   "at least I know how to reach THAT point."
   Over time, it covers more and more of the workspace.
   RECOMMENDATION: This could significantly help Phase 2
   since successes are currently very rare.
   In SB3: model = SAC(..., replay_buffer_class=HerReplayBuffer, ...)
   Needs GoalEnv format though (requires env restructuring).

4. SAC + PER (Prioritised Experience Replay)
   Instead of sampling uniformly from replay buffer,
   prioritise experiences where the error was large
   (i.e., things the model got very wrong → learn more from those).
   PROS: More sample efficient.
   In SB3: available via replay_buffer_class=PrioritizedReplayBuffer
   (in sb3-contrib extension).

RECOMMENDATION FOR YOUR PROJECT:
  Stay with SAC for now. The main bottleneck is the reward
  design and target sampling (which you've fixed). Change SAC
  only after exhausting reward tuning options.

  The single most impactful thing you could try beyond what
  you've done: HER replay buffer, once you've restructured
  the env as a GoalEnv.

SECTION 22 — YOUR IK IDEA — WILL IT WORK?
====================================================

YOUR IDEA:
Use Inverse Kinematics (like Unity ragdolls / Boston Dynamics
robot dog) — tell the arm "I want the end effector HERE at
THIS ORIENTATION, figure out the joint angles yourself."

THIS IS VALID AND WORTH THINKING ABOUT. Here's the nuance:

WHAT IK ACTUALLY DOES:
  IK solvers take a desired (position, orientation) as input
  and compute joint angles that achieve it. PyBullet has a
  built-in IK solver: calculateInverseKinematics().

THE GOOD NEWS:
  IK solves the target-reaching problem ANALYTICALLY, not
  with trial and error. For a given target it IMMEDIATELY
  tells you the joint angles needed. This is what Boston
  Dynamics and Unity use.

THE CATCH — TWO ISSUES:

ISSUE 1: IK may not be what you want as the WHOLE solution.
  IK answers "given target, what joint angles?"
  But for a SCAN, you need a sequence of positions (a path)
  and the ultrasound image quality varies with how you approach.
  IK gives you the endpoint, not the trajectory.

ISSUE 2: IK + RL could work together (HYBRID APPROACH).
  Here's a smart hybrid that could work well:

  a) Use IK to generate the joint angles that reach the target
  b) Use RL to learn HOW to move from current configuration
     to those angles without collisions and in a smooth path
  c) Or: use IK to warm-start the RL agent with good initial
     joint positions near the target

ISSUE 3: IK can fail or have multiple solutions.
  For a robot with many DOF (like this 9-DOF arm), there are
  MANY joint configurations that reach the same end effector
  position. The IK solver picks one, but it might not be the
  most collision-free or clinically appropriate one.

WOULD IT FIX THE ORIENTATION PROBLEM SPECIFICALLY?
  YES — potentially. PyBullet's IK solver can take a target
  position AND target orientation:
    calculateInverseKinematics(robot, end_link, target_pos, target_orn)

  If the target is reachable (which FK sampling guarantees),
  IK would immediately give you joint angles that put the
  end effector at that exact position with that exact orientation.

PRACTICAL SUGGESTION (if you want to explore this):
  1. After Phase 2, add a function that uses IK to compute
     target joint angles for the desired EE pose.
  2. Use those as the initial joint configuration at episode start
     (instead of always starting from zero).
  3. The RL agent then only needs to learn FINE ADJUSTMENT from
     near-correct positions, rather than learning from scratch.

  This is called "IK-initialised RL" — it can dramatically
  reduce the learning burden.

BOTTOM LINE: Your IK intuition is correct and sensible.
IK alone doesn't replace RL for the full problem (it can't
handle collisions, image quality, smooth paths), but IK as
a TOOL within the RL pipeline is a legitimate research direction.
