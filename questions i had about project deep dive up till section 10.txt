Forward Kinematics vs Inverse Kinematics

The best analogy: your arm reaching for a cup.

Forward Kinematics (FK) — "where does my hand end up?"

You know the angles of your shoulder, elbow, and wrist. FK answers: given those angles, where is your hand in space?

Shoulder at 45°, Elbow at 90°, Wrist at 30°
              ↓
         FK calculation
              ↓
    Hand is at position (x=0.4m, y=0.3m, z=1.1m)
    facing direction (quaternion)

Easy direction. One set of joint angles → one unique answer. No ambiguity.

In code this is getLinkState() — PyBullet does the FK math for you automatically when you set joint angles.

Inverse Kinematics (IK) — "what angles do I need to reach the cup?"

You see a cup at position (0.4, 0.3, 1.1). What shoulder/elbow/wrist angles get your hand there?

Target position: (x=0.4m, y=0.3m, z=1.1m)
              ↓
         IK calculation
              ↓
    Solution A: Shoulder 45°, Elbow 90°, Wrist 30°
    Solution B: Shoulder 60°, Elbow 70°, Wrist 15°
    Solution C: ... (many valid answers)
    OR: "impossible, can't reach" (joint limits exceeded)

Hard direction. One target position → potentially many joint angle solutions, or none at all. That's why IK is tricky — and why Unity ragdolls and Boston Dynamics use special solvers to pick the "best" solution.

Real-world example:
- GPS navigation uses FK thinking: "given I'm at this road junction and I drove 500m north, where am I?"
- Trying to reach a shelf uses IK thinking: "the shelf is there — how do I position my arm to grab it?"

In this project:
- Your FK-based target sampling uses FK: pick random joint angles → run FK → get the probe position → use that as the target. Guaranteed reachable.
- PyBullet has a built-in IK solver: calculateInverseKinematics(robot, end_link, target_pos, target_orn) — but it's not used in the current RL training.

Absolute Position vs Relative Distance — why both?

Think of it like GPS vs a compass.

Relative distance (Euclidean distance, index 0 in the observation) is like a compass that just says "target is 0.22m away." It tells the agent HOW FAR but not WHICH WAY.

Absolute positions (indices 5–10, the normalised x/y/z of both target and current position) are like GPS coordinates. They tell the agent WHERE things are in space.

You need both because:

Scenario: probe is 0.22m from target

With only distance:
  Agent knows: "I'm 0.22m away"
  Agent doesn't know: "am I above it? to the left? behind it?"
  → Can't decide which direction to move

With absolute positions too:
  Agent knows: "I'm at (0.1, 0.5, 0.2), target is at (-0.05, 0.45, 0.3)"
  → Can figure out: move left, forward, and up

Could the neural network compute the distance itself from the positions? Technically yes — but giving it the pre-computed distance as well makes learning faster. The network doesn't have to spend training steps figuring out the Pythagorean theorem. You're giving it the answer to the easy part so it can focus on the hard part (which joint angles produce the right movement).

Section 9 — Action Space (how the robot moves)

The neural network outputs 10 numbers, one per joint. Think of it like a mixing board with 10 sliders:

  NEURAL NETWORK OUTPUT (raw, always -1 to +1):
  ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
  │ J0  │ J1  │ J2  │ J3  │ J4  │ J5  │ J6  │ J7  │ J8  │ J9  │
  │-0.2 │+0.7 │ ??? │-0.1 │+0.5 │-0.8 │+0.3 │-0.4 │+0.6 │-0.1 │
  └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘

  AFTER SCALING (what actually gets sent to PyBullet):
  J0:  -0.2 ÷ 4   = -0.05 rad   ← gantry (small scale, linear rail)
  J1:  +0.7 × π   = +2.20 rad   ← rotational joint
  J2:  OVERRIDE   = -2.20 rad   ← always = -J1 (mechanical coupling)
  J3:  -0.1 × π   = -0.31 rad
  ...and so on

Why divide J0 by 4 instead of multiply by π? Because J0 is a LINEAR rail (slides up and down like a drawer). Moving it by π metres (~3.14m) would be enormous — the whole arm would slide off. Dividing by 4 keeps it in a sensible range (±0.25m).

The coupling on J2 (scaled[2] = -scaled[1]) models a real physical gear mechanism in the robot — two links connected by a parallelogram linkage that forces them to move together in opposite directions.

Section 10 — Reward (how the robot learns what's good)

Think of reward like a score in a video game. The agent wants to maximise its total score over the episode.

Phase 1 reward, step by step:

Every single timestep, the agent gets scored:

STEP 1: How far away am I right now?
  distance = 0.22m
  distance_normalised = 0.22 / 0.7533 = 0.29   (0 = at target, 1 = max away)

  PENALTY: reward -= 0.29    (constant drip of punishment for being away)

STEP 2: Did I get closer this step compared to last step?
  last step dist = 0.24m, this step = 0.22m
  progress = 0.24 - 0.22 = +0.02m   (positive = got closer)

  BONUS: reward += 5.0 × 0.02 = +0.10

STEP 3: Am I at the target?
  0.22m > 0.02m threshold → NO
  bonus = 0

  Total reward this step = -0.29 + 0.10 + 0 = -0.19

Over 300 steps, these tiny rewards add up. If the agent moves toward the target every step and reaches it, it gets the +100 jackpot at the end. If it wanders around, it accumulates penalties. The agent learns: "moving closer = good, staying still = bad, moving away = very bad."

Why the 5.0 multiplier on progress?

Without it, the "move closer" bonus (+0.02 per step) is much smaller than the "being away" penalty (-0.29). The agent could sit still doing nothing and its reward wouldn't change much — the penalty stays constant either way. The ×5 multiplier makes progress-chasing attractive: actively moving toward the target is worth more than passively existing near it.

Phase 2 reward — the gate:

                 3cm gate
                    │
─────────────────────│──────────────────── target (0cm)
          ↑          │          ↑
    "normal zone"    │    "orientation zone"
    only position    │    position + orientation
    reward active    │    reward active

If arm is here ──────→ ONLY position reward (-dist, +progress)

If arm crosses gate ──→ POSITION reward stays ON
                        PLUS orientation reward turns ON:
                          -0.05 × angle_error
                          +0.5  × angle_progress

The gate exists because orientation tuning requires tiny, precise movements. If the arm is still 20cm away, those tiny orientation adjustments do nothing useful — the robot should focus on position first. The gate enforces sequencing: position first, then orientation.

The drift penalty is a safety net. Imagine you finally get inside the gate and start adjusting your angle — but in doing so you accidentally wiggle a joint and drift 4cm back out. Without the drift penalty, the agent might not care (it still got some orientation reward). With the -10 penalty, drifting out costs more than it gained from orientation tuning, so the agent learns to stay put while rotating.
